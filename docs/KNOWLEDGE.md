## Owner rules v1.1 this game follows
- Organizer and host screens say "you". Zero first-person strings, kept by `apps/web/test/console-voice.test.ts`.
- The game starts by itself and numbers come by themselves. The two press-a-button formats ("you start", "you call") do **not** exist yet.
- People are invited by employee ID only. Every non-letter/number is dropped and capitals used, so `A-1101` = `A 1101` = `A/1101`. Unlisted IDs wait for yes or no. The invite log is for the organizer and hosts only.
- Paid only through the console's signed notice (`POST /api/console/paid`), once per order id. The game decides from its own tables (owner, size, not cancelled, not already paid). The same order id can be retried; a stuck order is released after 30 seconds (`MARKING_STUCK_MS`).
- Pay on the console page goes to the console (`https://console.corporatetambola.com/?game=bingo&eid=<game>`). No payment link, no "anyone can pay".
- Rupee sign, one privacy line, the fairness sentence (proved by `packages/beacon/test/fairness.test.ts`), no forbidden claims (`apps/web/test/owner-text.test.ts`, `apps/edge/test/owner-fixes-1-4-0.test.ts`).
- Money flags `PAY_VIA_CONSOLE` and `LOGIN_VIA_CONSOLE` stay OFF until the owner says go. The flag that closes this game's old pay routes is `PAY_VIA_CONSOLE`; `PAY_VIA_MONEYPENNY` is the console repository's own flag and does nothing here. Never put secrets in the repo.

## Things to know before you change anything
- `apps/edge/src/console-bridge/` is a byte-for-byte copy of the console repo's bridge (hashes in `MANIFEST.json`, checked by `bridge-copy.test.ts`). Do not edit it. A fix that belongs there goes to the console repo first.
- The stuck-order recovery lives in this game's wrapper (`releaseStaleMarking` and an order that can safely run twice in `consoleMarkPaid`), because the copied bridge leaves an order in "marking" after a one-off error.
- The server refuses `whoCanJoin: "anyone"` and makes a game that says nothing a game for its list (`openGamesAllowed` in `console-pay.ts`). On a settings save `closed` is accepted only when it is absent or `true`; `false`, `0`, `null`, `""` and anything else are refused with code `list-only` (1.5.1: `null` and `""` used to re-open a closed game). `LEGACY_OPEN_GAMES=1` is the old behaviour for old tests only (set by `apps/edge/test/with-terms.ts`); a test that wants the real rule sets it to `"0"` (`audit-1-5-1.test.ts`). Never set it on the live site.
- **The audit log never keeps a person's details in a row that lasts 365 days (1.5.2).** `redact(body, 0, true)` in `apps/edge/src/audit.ts` removes any field named like phone, mobile, name, label, e-mail, ID, location, ip or address, and any text that looks like a number or an e-mail; the person routes (`person`, `forget`, `unbind`, `mark`, `cohost`, `waiting`, `people`, `invites`, `org/host`, `org/team`) keep field names only. A player's and a Co-host's own rows go to the 23-hour shreddable part (`splitsPersonal`). If you add a route that takes a person's details, check it with `apps/edge/test/audit-1-5-2.test.ts`. A caller with no key adds a row only for a game that exists and only `AUDIT_ANON_PER_MIN` (20) / `AUDIT_GAME_PER_MIN` (300) a minute per network (in memory, per Worker copy; no database write).
- **"ID matched, not proven" is the owner's decision (BOSS; written in the suite's `SUITE_RULES.md`, which is not in this repository).** Anyone who types a listed ID gets that person's seat. A right ID is never counted and never limited per address. Do not add limits on right IDs. The help text says so (zc.js "Invite people with just an ID" box). Do not write "verified", "proven" or "secure" about an ID.
- **No name before joining, and no "wrong ID" limit (1.5.3).** `POST /api/z/:id/who` ("Is this you?") answers only `{ known: true|false }`, never a name (a name for a guessed ID was readable by anyone with the link). An ID that is not on the list is a normal request that waits for a yes or no, so it is NOT counted as a wrong try (the old 30-per-10-minutes `idMissOver` limit is gone: it locked out honest people). The waiting room has its own limit instead: one network (an IPv6 /64 is one network) may add at most `WAITING_PER_NETWORK` = 100 requests in any 30 minutes to one game (`waitingNetworkOver` in `people.ts`, one database statement, key `idmiss/<game>/wait/...`, erased with the game's data); the room as a whole still holds `WAITING_MAX` = 500. A person asking again is not counted again. A listed ID is never held back by it. Tests: `apps/edge/test/audit-1-5-3.test.ts`.
- **"Notify me when this game begins" is built and OFF (1.6.0).** The player page (`z.html`) loads `push-config.js` and `push-boot.js`. Only when `push-config.js` holds a plain https address (the ONE setting; empty today) does `push-boot.js` draw the block (`data-push-site="game"`, the game id from the link) and load `push-optin.js` and `push-optin.css`; until then nothing is drawn or requested and no call is made. Those two files and `sw-push-snippet.js` are copies of the corporate-push service's files at `f1e93f59f454`, never edited (`apps/web/test/push-optin.test.ts` checks their hashes). `pages/build.mjs` reads the same address (`pages/push-api.mjs`) and adds it to the player page's connect-src only when it is set. `zsw.js` loads `sw-push-snippet.js` (the push and notificationclick handlers) and leaves a push click to it. On the server, `apps/edge/src/push.ts` does only two things, only when `PUSH_URL` and `PUSH_ADMIN_KEY` are both set: ONE `POST /send` per game when `lifecycleTick` finds the game's start time has come (flag `engagement.push_sent_ms`, migration 0032; the flag is taken first in one statement, and given back only if the very first page was refused, within 30 minutes of the start), and `POST /purge` for the game's scope inside `erasePersonal`, which every deletion path goes through. The key is sent only as a header. Not done: more than 800 browsers for one game (20 pages of 40) are not sent to; the owner must put the same two privacy sentences into the one legal document (`terms.html` and the home site's copy) before switching it on; deploying the service, the VAPID keys and `PUSH_URL` / `PUSH_ADMIN_KEY` are the owner's steps.
- Any per-address key groups an IPv6 address by its /64 (`apps/edge/src/ipkey.ts`, `ipGroup`). Count in ONE statement (`INSERT ... ON CONFLICT DO UPDATE ... RETURNING`), never read-then-write.
- Run every test file as its own process. `apps/web/test/pages.test.ts` takes over 4 minutes: run it alone.
- Version number: change `version.json`, `package.json`, `apps/edge/package.json`, `apps/edge/src/releases.json` and `CHANGELOG.md` together (`apps/edge/test/version.test.ts` checks).
